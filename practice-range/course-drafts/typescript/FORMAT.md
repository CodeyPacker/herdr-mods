# Draft pack contract

Read `manifest.json` for the proposed format, `OUTLINE.md` for the outcome-to-assessment map, and `VALIDATION.md` for executed checks. This authoring draft lives outside the runtime catalog. Schema `1-draft` and content version `0.1.0-draft.1` identify the reviewed objects. Freezing v1 requires sample review.

| Record | Interpretation |
| --- | --- |
| C1 · Manifest | The ordered module list carries stable IDs, prerequisite module IDs and the concepts each module introduces. Planned rows have no file reference. Only sample rows can be opened from this artifact. The runner is selected by the registered language ID `typescript`. The compiler range is exactly 6.0.3, consistent with the pack lock and loader. |
| C2 · Module | Each `module.json` lists prerequisite concepts, observable outcomes with assessment IDs, ordered steps, prediction questions, examples, exercises, mapped drill IDs and a later review. Step, question, example and outcome keys are local to their parent module. The stored identity of question `predict-count` includes its module ID. |
| C3 · Lesson step | The `kind` selects a presentation such as prediction or modification. `text` is plain text or Markdown. Typed references select a question, example or task. A compile-error example declares expected diagnostic codes and one-based learner-file lines. A runnable example declares its expected output lines. |
| C4 · Exercise | Each task has its own JSON record. Paths to UTF-8 learner source, reference, alternative, fixture and wrong answers resolve relative to that record. `checks`, `typeChecks` and `rejects` are trusted expressions or statements in the existing TypeScript runner format. The task ID includes the course namespace. `feedback` explains a failure without requiring AI. |
| C5 · Project | `project/project.json` orders checkpoints. Paths resolve relative to that file. An editable entry maps a logical workspace filename to its starter. Supplied entries map immutable inputs. Trusted tests and author solutions live outside learner files. Each checkpoint states whether it is a runnable sample, plan or final specification. |
| C6 · Source | A bundled source is `{"kind":"bundled","path":"examples/board.ts"}` with its version inherited from the manifest. The learner may attach a repo by a per-machine attachment ID. A supplement could store `{"kind":"repo","attachmentId":"local-project","commit":"<full commit hash>","path":"src/tasks.ts","start":8,"end":13,"anchor":"type Task"}`. These placeholders illustrate required fields. Store actual repo references with the enrollment, keep bundled examples available, and resolve a missing anchor as an unavailable supplement. |
| C7 · Compatibility | This first draft has no earlier versions or replacements. An update would declare the source content version and each old ID, new ID and whether existing completion remains valid. A changed assessment can keep its answer history and require another attempt. An unmatched ID receives no credit. Pinned enrollments still need their original content. |

## What the runner already understands

`types.js` defines `Exercise`. Pass through `id`, `title`, `prompt`, `hints`, `mode`, `rules`, `checks`, `typeChecks` and `rejects`. Read the starter and solution files into the same-named string fields. Read one fixture's file into `declarations`. For a task with supplied sibling TypeScript modules, resolve packaged source references into the runner’s `modules` mapping of flat filename to text. In script mode the answer shares scope with the supplied declarations and checks. In module mode the check code imports the learner's exports as `answer`.

The runner accepts one answer string and fixture environment per call. The proposed adapter must run every declared fixture against the same saved answer. Group fixture results into one attempt and identify the failing fixture. Some starters or known wrong answers pass an individual fixture. The entire suite must pass. `verify.mjs` exercises this translation in an authoring process. It uses the existing checker for each call. Reference answers, alternatives, wrong answers and trusted checks should stay out of the learner workspace. Progressive hints and the reference solution use separate fields and separate reveal actions.

Only three tasks require a declaration form because the form is part of the explicit learning objective. The runner checks `const` for shelf-label, `let` for arrival-log, and `let` without an annotation for remaining. Other tasks allow equivalent control flow and syntax. The delivery modeling task checks assignability in both directions and rejects invalid assignments. It has no runtime result to compare.

The course loader, lesson renderer, fixture iteration on save, attempt aggregation, delayed review links and project navigation are integration work. Tutor's current outline/build/validation logic expects pinned repo excerpts and generates material on demand. The bundled file references and static predictions in this proposal need their own loading path. Tutor's known-language comparisons can remain optional.

## Bounded project workspace

The early checkpoint fits the existing script checker. The caller can read the single editable count file and pass it as an answer. The final project has two editable files and read-only imports with fixed flat names. A project session needs a separate workspace per enrollment and checkpoint, an explicit filename allowlist, and a reset that restores only that checkpoint's starters. On save, snapshot both edits, inject immutable fixture files and run trusted checks outside the writable folder. Run only the registered bounded compiler/checker with time/output limits and local inputs. Publish the latest save's result. Count one attempt per snapshot. On reset or review, preserve previous attempts and answers separately.

## Mutable records

Keep pack files immutable. A learner-owned enrollment records course/content version, entry path, current module/step, and per-module read or skipped status. Store the learner's question choices, timestamps, answer snapshots or references, and checkpoint edits there. An exercise attempt records the full task ID, fixture suite verdict, time, and assistance (none, hint level, AI help or solution shown). Preserve history across updates. Reading, skips and quiz responses have their own records. Only an unaided successful submission is evidence of independent work on that task. A delayed unaided pass adds another observation. A fixed universal mastery threshold is outside the proposal.
